Historical architecture snapshot

How pi-agents previously worked

A standalone guide to the extension's user-facing behavior, task-join semantics, durable mailbox model, safety boundaries, session ownership, runtime architecture, and failure recovery.

✓ 8 main-agent tools ✓ Real Pi AgentSession workers Session-owned mutable state Disk-backed mail No notification auto-wake

Overview

The shortest accurate description of the current system.

Runtime
In-process
Each worker is a real Pi AgentSession inside the owning host process.
Memory
Durable
Every identity writes Pi-native JSONL and resumes it on later wakes.
Coordination
Mailbox
File-per-envelope delivery; mail never interrupts a running subagent turn.
Ownership
Per main session
Two Pi conversations in one cwd get isolated mutable subagent worlds.
Core promise If the main agent delegates required work during a user turn, the host prevents it from publishing a final response until the exact task anchors reach terminal outcomes—unless the call explicitly uses background:true.
Not a daemon Subagents run only while their owning Pi host session is open. Their mail and memory remain on disk while the host is closed, but no independent service continues executing them.

Mental model

Think of the extension as a small, session-scoped actor system.

Identity

<type>/<id>

A stable address such as reviewer/auth. The type defines capabilities and role; the id names the instance's purview.

Private memory

Pi session JSONL

The transcript is not a summary database. It is an actual Pi session file that the SDK reopens, preserving the worker's conversation and tool history.

Communication

Durable envelopes

Tasks, questions, answers, reports, escalations, and errors are files routed through private mailboxes.

Human
Approves escalations, edits type definitions, controls the TUI, and can directly message workers.
Main Pi session
Delegates tasks, synthesizes results, denies—but cannot approve—blocked subagent operations.
pi-agents host
Owns task joins, scheduling, mail routing, durable state, generation fences, and TUI status.
Subagent sessions
Independent actor-like identities; one serialized turn per identity, parallelism across identities.

Tool surface

The main agent gets eight tools. Destructive and non-destructive powers stay deliberately separate.

ToolPurposeCompletion behavior
subagent_spawnGet-or-create a worker; optionally set team, lifetime, and first taskA supplied task joins the group unless background:true
subagent_sendSend/queue new work, answer a question, or deny an escalation by correlationUncorrelated send joins; correlated answer/deny creates no new task
subagent_steerRedirect only a currently running turnNo task anchor; returns steered:false if idle
subagent_statusRoster or detailed status, vitals, transcript tail, outstanding questionsRead-only; never perturbs a worker
subagent_collectRequest structured data validated against a supported JSON Schema subsetJoins unless background:true
subagent_awaitExplicit cancellable wait on an exact task/collect anchorReturns completed, attention, timeout, or retired
subagent_interruptAbort the current worker turn without destroying its identityOnly exact assignments in that turn become cancelled
subagent_retireArchive and permanently deregister an identityThe only destructive tool

Tools inside each subagent

send_message

Peer mail. expectReply:true creates a question; correlationId answers one.

report

Sends progress or a terminal final:true report to main. Structured collect data rides here.

ask

Asks main a non-blocking question. The worker ends its turn, goes dormant, and wakes with the answer quoted.

Coding tools are separately filtered by the worker type: read, bash, edit, write, grep, find, and ls are available only when policy permits.

Current-turn completion barrier

This is the orchestration feature that prevents “I delegated a review” from being mistaken for “the review is complete.”

1User input
A genuine interactive/RPC input opens a required-task group.
2Anchor creation
Task-bearing spawn/send/collect calls record exact envelope ids.
3Candidate final
If anchors remain, the visible answer becomes a waiting status.
4Durable await
Host waits for reports or attention without detaching timed-out polling.
5Same-run follow-up
Results are queued as Pi follow-ups; main incorporates them before finishing.

What joins automatically

  • A spawn with a task.
  • An uncorrelated main-to-worker send.
  • A collect request.
  • An uncorrelated peer message sent by a worker already in the required graph—this makes delegation transitive.

What remains awaited

Temporary attention

  • Questions to main
  • Human escalations
  • Provider/tool waits
  • Scheduler contention
  • Main-turn interruption

Missing terminal evidence

  • Progress-only reports
  • Plain assistant text without final:true
  • A dormant persistent worker whose task never finalized
  • Long-running tools or provider retries

Terminal outcomes

  • Exactly correlated report with payload.final:true.
  • Validated collect response correlated to its request id.
  • Fatal error evidence.
  • Retirement of the addressed generation.
  • Manual interruption of the exact turn assignments.

When main does not wait

CaseWhy no new required anchor
background:trueExplicit per-call detachment for task-bearing spawn, uncorrelated send, or collect
Spawn without a taskMain tracks work, not a persistent identity's lifetime
Correlated answer or escalation denialIt continues an existing task rather than creating new work
Status, steer, interrupt, retireControl/read operations do not create task assignments
Viewer user messageDirect human-to-worker channel is outside the main user-turn group
No active genuine user turnStartup or extension-generated activity is not retroactively attached
Host/session teardownThe live in-memory join ends; durable mail and session state remain where applicable
Important scope detail The required group is currently in memory. A host crash, shutdown, /reload, /new, or /fork ends that live join. Durable messages/results survive, but the old in-progress completion group itself is not reconstructed.

Mail and delivery

All ordinary worker input is mail. Steering is intentionally a separate power.

Envelope shape

{
  "id": "msg_<ulid>",
  "from": "reviewer/auth",
  "fromGenerationId": "gen_<32-hex>",
  "to": "main",
  "type": "report",
  "correlationId": "msg_<task-anchor>",
  "team": null,
  "hops": 1,
  "payload": { "text": "Review complete", "final": true },
  "sentAt": "2026-07-14T17:00:00.000Z"
}

Types

message, question, answer, report, escalation, error.

Ordering

ULID ids provide deterministic mailbox order. Correlation ids link answers, final reports, and collects to exact causes.

Generation fence

Agent-originated mail stamps fromGenerationId, so a reused address cannot satisfy an older join.

Subagent mailbox lifecycle

pending file→ delivery claimed→ Pi turn durably appended→ mailbox/.done

The runtime marks mail done only after prompt() and waitForIdle() complete and the receiving session has durable transcript evidence. A crash before that point causes labeled re-delivery.

Main mailbox lifecycle

pending→ .delivering→ host JSONL marker verified→ .done

Main delivery uses claim-first semantics. It parses complete host JSONL records structurally; a raw substring match cannot finalize mail. Await and ordinary digest delivery can register alternate accepted markers when they race.

No main auto-wake Mail arriving after main has finished does not start another main turn. Unrelated mail waits for the next genuine user turn. Required results are different: the active completion barrier feeds them into the same run as follow-ups.

Worker lifecycle and states

The registry has four live states; retirement removes the record entirely.

dormant→ mail/task → queued→ slot → running→ turn ends → dormant
running→ guarded tool → waiting→ human decision → running
any live state→ explicit/funeral → archived + deregistered

Persistent

  • Meaningful id or default main.
  • Get-or-create returns created:false for an existing identity.
  • Never auto-retires merely because a turn ended or a warning threshold was crossed.
  • Memory remains available across wakes and host restarts.

Oneshot

  • No explicit id; runtime assigns a random tmp-… id.
  • Auto-retires after an exact final report or fatal runtime error.
  • Warning thresholds do not trigger its funeral.
  • Archived transcript remains available until retention GC.

Concurrency: maxConcurrent controls running-turn slots (default 5). Extra turns queue FIFO. This is a scheduling bound, not a resource threshold that cancels work.

Type definitions and context

A type is the worker constitution: role, model, tools, path scope, and warning thresholds.

Discovery

~/.pi/agent/subagents/<type>.md      # global library
<project>/.pi/subagents/<type>.md   # project library; wins by name

Definitions must be independent regular files. Symlinks and multiply-linked files are rejected so an agent cannot retune itself through an unprotected alias.

Example

---
name: reviewer
description: Reviews authentication changes for correctness and security
model: openai-codex/gpt-5.3-codex-spark
thinking: high
projectContext: true
tools: [read, grep, find, ls]
readOnly: true
writePaths: ["src/auth/**"]
denyPaths: ["src/auth/migrations/**"]
maxTokensTotal: 30000
maxTurnMinutes: 15
maxContextCompactions: 2
---
You are a focused authentication reviewer. Report concrete findings.
Live resolution The type is resolved again at wake. Editing a type changes future wakes while the identity's transcript remains intact. The registry records the resolved type-file hash for visibility.

Context composition

  1. Pi's base agent system prompt.
  2. Project context files such as AGENTS.md, when projectContext:true.
  3. The type definition's Markdown body.
  4. Runtime identity: exact address, lifetime, purview, team roster, and communication rules.
  5. At each turn, a deterministic wake digest containing current mail and roster changes.

Subagent resource discovery is otherwise disabled: they do not automatically inherit arbitrary extensions, skills, prompts, or themes.

Sandbox and escalation

Static policy grants normal capabilities; ambiguous or out-of-scope mutation moves upward to the human.

Tool filter

Verb control

tools is an allowlist. readOnly:true strips mutators even if they appear in the list.

Path policy

Territory control

Precedence is readOnly > denyPaths > writePaths, with realpath/symlink-aware checking.

Bash classifier

Intent control

Mutating commands and operands are classified. Unknown or ambiguous mutation escalates rather than inheriting trust from a basename.

Always-protected state

  • The session-owned subagent state tree: registry, mailboxes, leases, archives, and escalations.
  • Global/project type-definition directories and their sibling settings files.
  • Ancestors whose mutation could replace or remove a protected prefix.

Escalation flow

1Tool call violates/ambiguously exceeds type policy
2Agent state becomes waiting; scheduler slot is released
3Durable record + escalation envelope reach main/human
4Human approves once or denies with optional note
5Turn reacquires a slot and the guarded tool resumes/errors
Approvals never flow downhill Main may deny an escalation by sending a correlated note. Main can never approve it. Only the human TUI can grant a one-time exception.

Teams and causal rails

Teams authorize peer communication without giving peers supervisory powers.

Team rule

Agent-to-agent mail is allowed only when sender and recipient share at least one team. The authorized team is stamped onto the envelope.

A teamless worker is solo: it can communicate with main but peer mail bounces.

Peer power limits

Peers may send/queue mail. They cannot spawn, steer, interrupt, retire, inspect status, read transcripts, or approve escalations.

maxHops: the remaining hard causal guard

Every message-triggered send increments causal depth. At the default depth 8, ordinary peer traffic bounces with guidance to report to main. Reports, escalations, and errors to main remain an escape route at any depth.

Why this differs from resource thresholds Token/time/compaction thresholds are warning-only. maxHops is a structural loop breaker for agent-to-agent ping-pong, so it still rejects over-depth causal traffic.

Warning-only thresholds

Resource thresholds inform the human; they do not act as hidden execution stops.

A genuine interactive/RPC user input resets the session turn/token accounting window. Direct viewer user input also opens a fresh window. Ordinary main-agent tool sends do not reset it.

Non-blocking warning widget

⚠ Subagent limit warning — reviewer/auth
maxTurnMinutes: 15/15 minutes. The agent is still running.
alt+ctrl+x interrupt only this subagent turn · alt+ctrl+i ignore
  • alt+ctrl+x includes a runtime-unique turnId. A delayed/stale warning cannot interrupt a newer turn at the same address.
  • Only exact task anchors present in the interrupted turn are cancelled; older or queued tasks at the same address remain required.
  • alt+ctrl+i dismisses the current card and lets execution continue.
  • Cards queue one at a time and do not capture the editor or block main.

There is no /agents resume command and no paused-autonomy queue-drain state.

Lifecycle commands

  • /agents <type>/<id> — jump directly to one live session.
  • /agents adopt-legacy — explicitly adopt inactive old cwd-wide state into the current empty persisted scope.

Architecture

The package is divided so durable state, runtime execution, policy, tools, and presentation have explicit boundaries.

index.ts
Extension entry. Registers tools/commands/shortcuts, owns host event hooks, main completion barrier, mailbox injection, warning cards, and overlay coordination.
core.ts
Facade used by tools and TUI. Wires layout → settings → runtime, tracks required anchors, exposes durable await/drain, joins registry/teams/mail for read surfaces.
runtime/
types.ts is the swap-point interface. in-process.ts builds real AgentSessions, serializes per-agent turns, manages assignment correlation, vitals, generation fences, and funerals. scheduler.ts owns FIFO slots.
mail/
Envelope validation, file mailboxes, collect schema validation, routing/team/hop checks, deterministic wake digests, host claims, and delivery reconciliation.
store/
Single path authority, registry, teams, settings, archives/GC, process identity, host leases, session manifests, adoption, rollback, and locking.
sandbox/
Tool filtering, realpath-aware path policy, bash mutation classification, escalation persistence, wait/resume, and human decisions.
typedefs/ + context/
Restricted frontmatter parser, hardened discovery, type precedence, project context loading, identity/team prompt composition.
tools/ + tui/
Eight main tools, three subagent communication tools, status widget, picker, viewer, and escalation prompt.

Dependency rule

Tools and TUI talk to core.ts, not directly to runtime/in-process.ts. The runtime is held behind runtime/types.ts, preserving a future daemon/RPC implementation path without rewriting upper layers.

One worker turn

  1. Deliverer atomically writes an envelope to the recipient mailbox.
  2. A dormant recipient is marked/scheduled; running or waiting recipients hold mail for the boundary.
  3. Runtime obtains the per-agent chain, host lifecycle lock checks, generation fence, run-owner claim, and scheduler slot.
  4. Pending envelopes are claimed; a deterministic wake digest is composed.
  5. The worker's Pi AgentSession receives the digest as its user prompt.
  6. Tool calls may send mail, report, ask, or block in a human escalation while releasing the scheduler slot.
  7. After durable idle, triggering envelopes move to .done, vitals update, exact final assignments clear, and held mail schedules the next serialized turn.

Durability, locking, and recovery

The implementation assumes crashes can occur between any two filesystem operations.

Ownership fences

  • Host-scope lease prevents two live Pi processes from consuming one main-session scope.
  • Per-agent run-owner marker prevents two runtimes from appending one worker JSONL.
  • PID plus process-start identity prevents PID reuse from impersonating an old owner.
  • Random generationId fences address reuse.

Atomic publication

  • Registry/team updates use serialized atomic read-modify-write.
  • Locks publish complete owner records through private candidates and atomic hard-link publication.
  • Stale lock reclamation uses generation-specific directory leases to avoid unlink/ABA races.
  • Operational I/O uncertainty retries or fails closed.

Crash recovery

  • Stale running/queued/waiting states reconcile at startup.
  • Unverified host delivery is requeued only under exclusive host ownership.
  • Assignment anchors reconstruct when envelope delivery beat anchor persistence.
  • Orphaned escalations cancel unless a live foreign owner still holds the wait.

Retirement recovery

  • Durable retirement intent records final/error evidence.
  • Archive/team scrub completes before deregistration publishes address reuse.
  • Startup completes crash-interrupted funerals.
  • Future mail bounces; already-held peer mail is not silently buried.

Legacy migration

Old cwd-wide state is detected but never auto-assigned. Adoption requires a human command, an empty persisted target, shared adoption locking, exact inode validation, symlink rejection, a retained inactive backup, and a protocol activation boundary. Rollback succeeds only while the adopted state fingerprint has not diverged.

Settings

Settings are optional sidecar JSON files, merged field by field.

~/.pi/agent/subagents.json      # global
<project>/.pi/subagents.json    # project override
{
  "maxConcurrent": 5,
  "maxHops": 8,
  "autonomousTurns": 40,
  "autonomousTokens": 500000,
  "archiveGcDays": 7,
  "maxTokensTotal": null,
  "maxTurnMinutes": null,
  "maxContextCompactions": null
}
  • Precedence: defaults → global → project → programmatic overrides.
  • All fields except maxConcurrent are re-read at every genuine user turn; scheduler capacity applies after core recreation/reload.
  • Unknown keys and invalid values warn instead of crashing the extension.
  • A malformed/unreadable file retains its last-known-good layer; an intentionally missing file removes that layer.
  • null clears an optional per-agent warning threshold.
  • There is no autoWake setting.

End-to-end examples

Concrete scenarios showing how the pieces compose.

Required delegated review
  1. Main calls subagent_spawn with a review task.
  2. Runtime writes a task envelope, records the assignment anchor, and wakes the reviewer.
  3. Main attempts to finish; message_end replaces the answer with “Waiting for 1 required subagent task.”
  4. Reviewer sends progress; progress is durable but does not settle the anchor.
  5. Reviewer sends an exactly correlated final:true report.
  6. Host await claims it, verifies delivery through the main JSONL marker, and injects it as a follow-up.
  7. Main incorporates findings and may now publish its final response.
Peer delegation inside required work
  1. Required worker A sends an uncorrelated task message to teammate B.
  2. The runtime records B's assignment and the core adds B's envelope to the same required graph.
  3. A's final does not hide B's outstanding task.
  4. B's report to main auto-correlates to the peer assignment id.
  5. Main receives both terminal outcomes before completion.
Worker asks main a question
  1. Worker calls ask and ends its turn.
  2. Await returns attention with the question, but the original task remains required.
  3. Main answers with subagent_send and the question envelope id as correlationId.
  4. The answer wakes the worker with its original question quoted.
  5. The worker continues and eventually sends its final report.
Blocked write requiring a human
  1. A write escapes writePaths or bash intent is ambiguous.
  2. The tool pauses, worker becomes waiting, and its scheduler slot is released.
  3. Main sees attention and can deny with a correlated note; only the human can approve once.
  4. After decision, the worker reacquires a slot and its tool either proceeds or returns an error.
Explicit background work
  1. Main uses background:true on task-bearing spawn/send/collect.
  2. The envelope still routes normally and the worker still runs.
  3. No current-turn required anchor is added.
  4. The eventual result remains durable in main's mailbox but never auto-wakes an idle main session.
  5. A later genuine user turn can drain it.

Known logic gaps and boundaries

An honest register of the current implementation's open consistency gaps, missing controls, UX limitations, and intentional tradeoffs. “Known” is not a proof that no undiscovered defect exists.

Highest-priority open gaps

GapCurrent consequenceLikely correction
Required group is memory-onlyCrash, shutdown, or /reload preserves mail and workers but loses which anchors were mandatory for the interrupted user turn.Persist a group id plus exact anchors and safely rehydrate it with the owning main session.
Host abort is not wired into the barrier controllerIf the user aborts while agent_end is already waiting, the internal await can remain blocked until its 900-second polling interval returns.Forward ctx.signal into the active barrier AbortController and remove the listener in finally.

A later wake can execute “cancelled” work and produce an unjoined result.Choose one coherent contract: preserve the join on interrupt, or durably mark/quarantine exact triggering envelopes as cancelled.

Semantic and coordination gaps

message conflates task and FYI

An uncorrelated peer message from required work is treated as delegated work. Harmless informational chatter can therefore create a required anchor that never receives a final. There is no peer-side background flag or explicit task/notice distinction.

Peer result routing is indirect

A delegated child reports final to main, not automatically to its parent. If the parent needs the value, it must use the question/answer path or another message—whose intent is itself ambiguous.

background:true is model-controlled

The main LLM can choose detachment without separate human authorization. This is explicit in the tool call, but not necessarily explicit to the human.

Main's draft answer is replaced

When the barrier catches a premature final, it replaces the full assistant draft with a generic waiting sentence. Useful synthesis already written in that draft is not preserved for the follow-up turn.

Required graph has little user visibility

The user sees a count but not a durable task-group view with anchor, owner, age, attention state, and reason it remains blocked.

Urgent detached mail is intentionally quiet

Errors, escalations, and reports outside an active required group do not auto-wake main. The TUI can surface human escalations, but headless main processing waits for another real input.

Warnings and settings gaps

  • Headless/RPC visibility: warning events are queued for the TUI widget; non-TUI modes have no equivalent structured warning/control channel and an unattended queue can grow.
  • Post-turn wording: token/compaction warnings may be emitted after the turn ended, while the card always says “The agent is still running” and offers an interrupt that safely becomes a stale no-op.
  • Session-wide attribution: the worker that happens to cross a global turn/token threshold is named in the warning even though consumption belongs to the whole session window.
  • Ephemeral warning state: queued warnings and per-handle “already warned” state are not durable, so restart can lose cards or re-emit per-agent warnings.
  • Partial-invalid settings edits: valid JSON with one mistyped field is treated as a successful layer without that field, so the previous field value can fall back to a lower layer/default. Last-known-good retention applies only to whole-file read/parse failures.
  • Terminology drift: some internal comments/prompts and historical specs still say “budget exhaustion” or “ceiling,” although current resource thresholds do not stop execution.

Scale and data-shape gaps

  • Await text is bounded, but structured report/collect data can still be large and is serialized into a main follow-up, creating context/memory pressure.
  • Agent transcripts are long-lived Pi JSONL. Pi compaction helps model context, but disk history grows until retirement/manual cleanup.
  • Mailbox audit/quarantine, collect metadata, and generation-anchor retention share time-based GC. Very old explicit awaits eventually operate outside their original retained generation-index window.
  • The supported collect validator is intentionally a small JSON Schema subset; ignored keywords can make a caller believe a stronger schema was enforced unless it reads the tool contract.

Intentional architectural boundaries

Not an always-on daemon

Closing the owning host stops in-process execution. Durable state lets the scope recover, but work does not continue on an independent service.

Live join is not crash-persisted

Task/report anchors are durable, but the exact set designated “required for this live user turn” is currently in memory.

Persistent lifetime is never joined

Main waits for exact assignments, not for the identity to cease existing. A persistent worker normally returns to dormant.

Supported collect schema is a subset

Validation supports type, properties, required, items, enum, const, and additionalProperties:false. Other JSON Schema keywords are ignored.

Main cannot approve

The orchestration model may deny a blocked operation but cannot grant new capability. This is a deliberate non-delegable human power.
